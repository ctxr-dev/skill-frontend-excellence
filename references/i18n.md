# Internationalization and Localization

## Why this exists

`ui-ux.md` carries a seven-line Localization stub that names the topic and points elsewhere. The depth lives here. Use this file when adding a locale, rendering text or numbers per user preference, supporting an RTL script, debugging a layout that broke on translation, or wiring `hreflang` on an indexable page.

Two definitions kept consistent across the file: i18n is the engineering work that makes the product capable of being localized (extract strings, support bidi, use `Intl`); l10n is the per-locale content work (translate, vet, ship). i18n is a codebase property; l10n is a release artefact.

## Translation pipeline UX

The pipeline is a UX surface for the translator, the engineer, and the user. All three sets of decisions live in this section.

### String extraction

Every user-facing string lives in a resource file the translator can read, not in the source code. The source is the catalogue, not the component.

- Extract every string into a flat key namespace (`account.recovery.email_sent`) or a hierarchical structure the translation tool understands.
- Keys are stable; strings are translatable. Renaming a key invalidates every translation.
- Comments alongside the key tell the translator the context. ("Button label on the recovery confirmation modal.")
- Screenshots attached to the key remove ambiguity for non-native engineers and translators.

### Missing-key fallback rendering

A locale that lacks a key falls back to the default locale (usually English). Three rules:

1. In production, render the default-locale string silently. Never render the key (`account.recovery.email_sent`).
2. In development, render the key in a high-visibility wrapper so engineers spot missing translations immediately (`[[account.recovery.email_sent]]`).
3. In staging, render the key alongside the default-locale string so QA can confirm coverage before launch.

This split is non-negotiable. Production must read like a real localized product; development must shout when strings are missing.

### Length expansion buffer

Translated strings grow. Plan for it.

- German is about 30% longer than English on average; some technical terms expand to 60%.
- Russian and Polish grow about 20%.
- Chinese and Japanese shrink to about 70% but the glyphs are denser.

Design buffer rules:

- Buttons reserve 30% extra horizontal room. A "Save" button that hugs its text at 60 pixels in English needs to fit "Speichern" at 80 pixels in German.
- Form labels wrap to two lines without breaking layout. Labels next to inputs reserve the wrap height.
- Card titles allow at least one extra line. Two-line max on every card; three on long-form locales.
- Cells in tables that hold action labels grow with the label, not against it.

Test with the longest reasonable translation, not the English original.

### Never ship untranslated keys to prod

If a key is missing in a locale, the build fails or the deploy is blocked. The pipeline reports the missing keys per locale on every PR. A "release candidate" with 92% translation coverage ships at 92% only if the team has explicitly accepted the gap.

## `Intl.*` at depth

The `Intl` namespace is the standard. Use it instead of any project-specific date or number formatter. The constructors are cheap; memoise per locale.

### `Intl.NumberFormat`

Use for currency, percent, units, and decimal display. Locale-aware decimal separator, grouping separator, currency placement, and unit pluralisation come for free.

```js
const fmt = new Intl.NumberFormat("de-DE", { style: "currency", currency: "EUR" });
fmt.format(1234.56); // "1.234,56 €"

const pct = new Intl.NumberFormat("en-US", { style: "percent", maximumFractionDigits: 1 });
pct.format(0.078); // "7.8%"

const dist = new Intl.NumberFormat("en-US", { style: "unit", unit: "kilometer" });
dist.format(42); // "42 km"
```

Pitfalls:

- Currency display: the constructor takes a currency code (`USD`, `EUR`), not a symbol. The symbol is rendered per locale.
- Significant digits vs fraction digits: pick one (`minimumFractionDigits` plus `maximumFractionDigits`, or `minimumSignificantDigits` plus `maximumSignificantDigits`).
- `useGrouping: false` disables the grouping separator (useful for IDs that look like numbers).

### `Intl.DateTimeFormat`

Use for any user-visible date or time. Pass an explicit time zone for server-generated values; let the constructor infer the user's zone for client-side values.

```js
const fmt = new Intl.DateTimeFormat("ja-JP", { dateStyle: "long", timeZone: "Asia/Tokyo" });
fmt.format(new Date()); // locale long date in Tokyo time
```

Styles to know:

- `dateStyle` and `timeStyle` (`full`, `long`, `medium`, `short`): the simple path; the constructor picks a locale-appropriate ordering and separator.
- `era` (`short`, `long`): adds AD or BC; useful for historical content.
- `calendar` (`gregory`, `japanese`, `buddhist`, `hebrew`, `islamic`): overrides the locale's default calendar.

For relative times ("2 days ago"), use `Intl.RelativeTimeFormat` instead of constructing a string from `DateTimeFormat`.

### `Intl.PluralRules`

Returns the plural category for a value in a locale: `zero`, `one`, `two`, `few`, `many`, `other`. Every locale uses a subset of these; English uses two, Arabic uses six.

```js
const pr = new Intl.PluralRules("ar");
pr.select(0); // "zero"
pr.select(1); // "one"
pr.select(2); // "two"
pr.select(11); // "many"
```

Never write `count === 1 ? "item" : "items"`. The first interpretation breaks on every locale that has more than two categories. Use ICU MessageFormat, Fluent, or a key-per-category table.

### `Intl.ListFormat`

Joins items into a locale-aware list ("a, b, and c" in English; ", and" is two characters in some locales, " et " in French between the last two items).

```js
const fmt = new Intl.ListFormat("en", { style: "long", type: "conjunction" });
fmt.format(["red", "green", "blue"]); // "red, green, and blue"

const dis = new Intl.ListFormat("en", { style: "long", type: "disjunction" });
dis.format(["red", "green", "blue"]); // "red, green, or blue"
```

Types: `conjunction` (and), `disjunction` (or), `unit` (no joiner, for unit lists). Styles: `long`, `short`, `narrow`.

### `Intl.RelativeTimeFormat`

Formats relative times in the user's locale, with the right preposition and the right tense.

```js
const rtf = new Intl.RelativeTimeFormat("en", { numeric: "auto" });
rtf.format(-1, "day"); // "yesterday" (not "1 day ago")
rtf.format(2, "hour"); // "in 2 hours"

const rtfFr = new Intl.RelativeTimeFormat("fr", { numeric: "auto" });
rtfFr.format(-1, "day"); // "hier"
```

Use `numeric: "auto"` for the natural-language form ("yesterday"); `numeric: "always"` for the numeric form ("1 day ago").

Compute the delta and pick the unit (second, minute, hour, day, week, month, year) yourself; `RelativeTimeFormat` does the formatting, not the bucketing.

### `Intl.Segmenter`

Splits text into grapheme clusters, words, or sentences with locale-aware boundary detection. Critical for languages without spaces between words (Japanese, Chinese, Thai).

```js
const seg = new Intl.Segmenter("ja", { granularity: "word" });
const segments = [...seg.segment("これは日本語の文章です。")];
// segments[].segment is each word; .isWordLike distinguishes words from punctuation
```

Use cases: word count in a translator-facing dashboard, locale-aware truncation, search highlighting, sentence-level summarisation. The default `String.prototype.split(/\s+/)` is wrong for any CJK script.

## Plural rules in depth

Plural categories per locale, from CLDR:

| Locale | Categories |
|--------|-----------|
| English | `one`, `other` (2) |
| French | `one`, `many`, `other` (3) |
| Russian | `one`, `few`, `many`, `other` (4) |
| Polish | `one`, `few`, `many`, `other` (4) |
| Arabic | `zero`, `one`, `two`, `few`, `many`, `other` (6) |
| Welsh | `zero`, `one`, `two`, `few`, `many`, `other` (6) |
| Japanese | `other` (1) |
| Chinese | `other` (1) |

Anti-patterns:

- `count === 1 ? "item" : "items"`. Wrong on every locale with more than two categories.
- `count > 1 ? plural : singular`. Wrong for zero, and for locales with a separate `zero` category.
- Concatenating "(s)". Reads as a typo; does not translate.
- Picking the plural in code, not in the translation. The translator cannot fix what they cannot see.

The correct shape:

```js
const pr = new Intl.PluralRules(locale);
const category = pr.select(count); // "one", "other", "few", etc.
const message = strings[`cart.items.${category}`].replace("{count}", count);
```

Or use ICU MessageFormat in the resource file:

```text
cart.items = {count, plural, =0 {Your cart is empty} one {# item} other {# items}}
```

The `=0` exact-match special-cases zero independently of the category; CLDR `zero` covers a different concept (some Slavic languages use the `zero` category for numbers ending in 0).

## Bidi correctness beyond `dir="rtl"`

Adding `dir="rtl"` to `<html>` swaps the writing direction but leaves three classes of bug.

### Mirrored icons

Directional icons (chevrons, back-arrows, send-arrows, arrow-callouts) point the wrong way in RTL. Three approaches:

1. **CSS mirroring via `dir`.** A single icon, flipped per direction with a logical selector (`[dir="rtl"] .icon-chevron-back { transform: scaleX(-1); }`).
2. **Pre-mirrored SVG sets.** Ship `chevron-back-ltr.svg` and `chevron-back-rtl.svg`; the component picks per direction. Use when the visual asymmetry is meaningful (a hand-drawn arrow that does not reflect cleanly).
3. **Logical-by-design SVGs.** Symmetric icons (search, settings, close) need no mirroring. Audit the icon set once; mark the directional ones.

Do not mirror: branded logos, country flags, content images, math notation, time-of-day icons (a clock face), media-control icons (play, pause, stop).

### Logical properties everywhere

Use logical CSS properties; never directional ones for layout.

| Old (directional) | New (logical) |
|-------------------|---------------|
| `margin-left` | `margin-inline-start` |
| `margin-right` | `margin-inline-end` |
| `padding-left` | `padding-inline-start` |
| `padding-right` | `padding-inline-end` |
| `left: 0` | `inset-inline-start: 0` |
| `right: 0` | `inset-inline-end: 0` |
| `border-left` | `border-inline-start` |
| `text-align: left` | `text-align: start` |
| `float: left` | `float: inline-start` |

The logical properties flip with `dir="rtl"` automatically. Directional properties do not.

### Locale-aware navigation order

In RTL, the back button lives on the right side of a top bar, not the left. The primary action of a form lives on the left, not the right. The mental model "back is behind me" is mirrored.

Logical-property layout handles most of this for free. The mistakes are usually:

- Hardcoded `position: absolute; left: 1rem` for a back chevron. Use `inset-inline-start`.
- A fixed-direction icon-only button (an SVG with the arrow baked in). Mirror the icon.
- Keyboard shortcuts on left and right arrow keys for previous and next. The physical arrows do not change with `dir`; the logical mapping does. In RTL, left arrow advances, right arrow goes back. Bind to logical concepts (`next`, `previous`), not physical keys, and route via the dir attribute.

### ICU bidi-isolate (`<bdi>`)

When user-generated content is mixed with template text, the bidi algorithm sometimes joins runs and produces unreadable lines.

```html
<p>The author is <bdi>{userName}</bdi>.</p>
```

`<bdi>` isolates the embedded run from the surrounding directionality. Use for usernames, addresses, free-form titles, anything user-entered that may contain bidi characters.

For programmatic isolation, the Unicode bidi isolate characters (`U+2068`, `U+2069`) wrap a string without HTML markup; useful in JS where the result feeds into a non-HTML context.

## Locale-aware navigation

The user's mental model of "where the back button is" is shaped by their language direction. Two places this matters:

### Keyboard navigation in scroll containers

Arrow-key navigation in a horizontal list must follow logical direction.

- In LTR, the right arrow advances; the left arrow goes back.
- In RTL, the left arrow advances; the right arrow goes back.

Bind handlers to logical concepts (`onNext`, `onPrevious`) and route via a `dir`-aware adapter at the boundary:

```js
const dir = document.documentElement.dir || "ltr";
const advance = dir === "rtl" ? "ArrowLeft" : "ArrowRight";
const reverse = dir === "rtl" ? "ArrowRight" : "ArrowLeft";
```

Page Up, Page Down, Home, End are logical and do not flip.

### Carousel and gallery direction

A carousel's "next" slide moves in the locale's reading direction. In RTL, the next slide enters from the left, not the right. Swipe direction follows the same rule.

Native scroll containers handle this when the parent has `dir="rtl"` and the children flow naturally. Custom carousels must invert their swipe handlers per `dir`.

### Form primary action placement

Submit (the primary action) lives at the inline end of the form. Cancel lives at the inline start. In LTR, primary is on the right; in RTL, on the left.

Use `flex-direction: row` with logical justification; do not hardcode `justify-content: flex-end` (which flips correctly) or position the buttons by left and right (which does not).

## hreflang and canonical interaction

`hreflang` tells search engines which URL serves which locale. `<link rel="canonical">` tells search engines which URL is the canonical version for ranking. The two interact.

### The bidirectional rule

Every locale references every other locale plus `x-default` for the fallback. Five locales means five `<link rel="alternate" hreflang>` entries on every page, one of which references the page's own URL.

```html
<link rel="alternate" hreflang="en-US" href="https://your-domain.com/en/" />
<link rel="alternate" hreflang="de-DE" href="https://your-domain.com/de/" />
<link rel="alternate" hreflang="ja-JP" href="https://your-domain.com/ja/" />
<link rel="alternate" hreflang="x-default" href="https://your-domain.com/en/" />
<link rel="canonical" href="https://your-domain.com/en/" />
```

If page A references page B but B does not reference A, search engines drop the cluster. The cluster is symmetric or it is broken.

### The canonical chain

Every locale page's canonical points at its own locale URL, not at the default locale's URL. Cross-locale canonicalisation tells search engines to fold every locale into the default and is almost always wrong.

The exception: a duplicate-content page that should not rank in its own right (a print version, a `?utm=` variant) canonicalises to the indexable version, including when the indexable version is a different locale only if the duplicate is genuinely the same content. Default to "each locale canonicalises to itself."

### `x-default`

`x-default` is the "best guess" fallback for a user whose locale is not in the set. Typically the default locale (English). It is a hint; search engines treat it as one input among many.

If the site uses geolocation to pick a locale, `x-default` should point at the locale-selection page, not at any specific locale.

## Translation-pipeline operational notes

### Tool choice

| Tool | Strength | Weakness |
|------|---------|----------|
| Crowdin | In-context preview, translator-friendly | Per-string pricing scales fast |
| Lokalise | Strong CLI and API | Less polished translator UX |
| Phrase | Versioning and branching parity with code | Heavier UI; learning curve |
| Open-source (Weblate, Pontoon) | Self-hosted; no per-seat fee | Requires ops capacity |

Pick the tool by where the bottleneck lives: translators (Crowdin), engineers (Lokalise), localization managers (Phrase), budget (open source).

### Format choice

| Format | Strength | Weakness |
|--------|---------|----------|
| ICU MessageFormat | Most expressive plural and select syntax; tooling support | Slight authoring complexity |
| Fluent (Mozilla) | Multi-line, expressive, designed for translation | Smaller ecosystem |
| GNU gettext (`.po`) | Massive ecosystem; every locale tool supports it | Plural syntax is limited; not great for select |
| Flat JSON | Trivial; works everywhere | Plural handling is per-key duplication |

Default to ICU MessageFormat. Use Fluent when grammatical agreement (gender, case) matters in many locales. Use gettext when integrating with a legacy chain.

## Locale negotiation

Two signals tell the product which locale to render: the `Accept-Language` header (passive, from the browser) and an explicit user choice (active, from a settings menu or URL prefix).

Rules:

1. An explicit user choice always wins. Never override it with `Accept-Language`.
2. Persist the choice in a cookie the server can read on the next request.
3. The first visit (no cookie) uses `Accept-Language` to pick a default.
4. If `Accept-Language` resolves to a locale the product does not support, fall back to the default locale and surface the available locales prominently.
5. The URL is canonical: locale lives in the path (`/en/`, `/de/`) or the subdomain (`en.your-domain.com`). The cookie persists the choice; the URL communicates it.

Never block on `Accept-Language` resolution; render the default locale immediately and switch after the cookie is read if needed.

## Currency display

Currencies share symbols across countries. `$` is USD, CAD, AUD, NZD, MXN, and twenty more. `£` is GBP and EGP. `kr` is at least four currencies.

Rules:

- Always show the currency code alongside an ambiguous symbol on first reference: "USD$ 12.99", "CAD$ 12.99". On second reference within the same view, the symbol alone is enough.
- For prices in the user's own currency, the symbol-only form is usually fine; the user already knows the currency.
- For prices that vary by region (a marketplace, a checkout flow), default to the disambiguated form everywhere.
- `Intl.NumberFormat` with `style: "currency"` and the right currency code does the right thing per locale. Pass the code, not the symbol.

## Numbers in forms

The decimal separator differs by locale.

- Period in en-US, en-GB, ja-JP, zh-CN: `1,234.56`.
- Comma in de-DE, fr-FR, es-ES, pt-BR, ru-RU: `1.234,56`.
- Space (or no separator) in some technical contexts.

Rules:

- Parse user input in the user's locale. `Intl.NumberFormat.formatToParts` exposes the separators; reverse-parsing is straightforward.
- Accept both forms for forgiveness on copy-paste. A user pasting `1234.56` into a `de-DE` form should not fail validation.
- On `<input type="number">` the browser handles locale-aware input itself. Use `<input inputmode="decimal">` on text inputs for prices to bring up the right mobile keyboard.
- Store and transmit numbers as locale-neutral (period as decimal, no grouping). Format on display.
